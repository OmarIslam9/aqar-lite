# عقار لايت — بيع الوحدات العقارية بالتقسيط

نسخة مصغّرة لنظام متعدد الشركات (multi-tenant): حجز وحدة 72 ساعة ← عقد مسودة ← اعتماد المحاسب ← جدول أقساط ← دفعات.

## التشغيل

المتطلبات: Python 3.10+ (جُرّب على 3.12) وPostgreSQL 14+ شغّال محلياً (مثلاً Postgres.app على macOS).

```bash
git clone <رابط المستودع> && cd <المجلد>
./run.sh
```
افتح http://127.0.0.1:8000. السكربت (آمن للتكرار): ينشئ `.venv` ويثبّت المكتبات، وينسخ `.env.example` إلى `.env`، وينشئ قاعدة البيانات إن لم تكن موجودة، وينفّذ الـ migrations والـ seed، ثم يشغّل gunicorn. لاستخدام إصدار Python محدد: `PYTHON=python3.12 ./run.sh`. السكربت يفترض أن `createdb` و`psql` يتصلان بقاعدتك المحلية بمستخدمك الحالي، وإلا اضبط متغيرات `PG*` أو أنشئ القاعدة يدوياً.

يدوياً:
```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env && createdb aqar
export FLASK_APP=app
flask db upgrade && flask seed
flask run --port 5001
```

الاختبارات: `createdb aqar_test` ثم `pytest -q`. (يرفض الاختبار التشغيل على أي قاعدة اسمها لا ينتهي بـ `_test`.)

كلمة مرور كل الحسابات التجريبية: `Passw0rd!2026` (تتغير بـ `SEED_PASSWORD` قبل أول `flask seed`).

| الدور | شركة النخيل | شركة الواحة |
|---|---|---|
| مدير | manager1@nakheel.test | manager1@waha.test |
| محاسب | accountant1@nakheel.test | accountant1@waha.test |
| مندوب 1 | sales1@nakheel.test | sales1@waha.test |
| مندوب 2 | sales2@nakheel.test | sales2@waha.test |

لكل شركة 12 وحدة، ولكل مندوب 3 عملاء.

للإنتاج (خلف HTTPS): `COOKIE_SECURE=1` و`SECRET_KEY` عشوائي لا يقل عن 32 حرفاً ولا يبدأ بـ `dev-` (يرفض التطبيق التشغيل بغير ذلك)، مثلاً: `python -c "import secrets; print(secrets.token_hex(32))"`. وخلف reverse proxy فعّل `TRUST_PROXY=1`.

## القرارات التقنية

- **Flask بدل Next.js، وسكربت `run.sh` بدل `docker compose up`:** الاثنان تم الاتفاق عليهما مع الشركة ([الرياده الخضراء]). الواجهة قوالب Jinja2 تُرسم في الخادم بدون JavaScript تقريباً، فلا توكنات في المتصفح، والـ CSP صارم (`script-src 'self'`).
- **PostgreSQL + SQLAlchemy 2 + Alembic.** البديل المرفوض: SQLite، لأنه لا يدعم قفل الصفوف الذي يعتمد عليه الحجز المتزامن.
- **المبالغ أعداد صحيحة بالهللات** (`*_minor`، BIGINT)، وDecimal عند الحدود فقط. لا float في أي مكان. مجموع الأقساط يساوي السعر النهائي حتى آخر هللة، والباقي من القسمة يذهب لآخر قسط.
- **طبقات:** `routes` (HTTP فقط) ← `services` (منطق ومعاملات) ← `schedule.py` و`allocation.py` (دوال نقية بلا قاعدة بيانات). الخدمات لا تعمل commit، والـ route هو صاحب الـ transaction.
- **التزامن:** قفل صف الوحدة (`SELECT … FOR UPDATE`) عند الحجز، وقفل العقد ثم أقساطه عند الدفع، وترتيب أقفال ثابت (الوحدة ← العقد ← الحجز) لمنع deadlock. فوقها partial unique index على الحجز النشط للوحدة كخط دفاع أخير.
- **انتهاء الحجز بدون cron:** كل طلب يلمس الوحدات أو الحجوزات يفك المنتهية أولاً (`expire_due`، مع `SKIP LOCKED`). البديل المرفوض: job دوري، لأنه يضيف مكوّناً يمكن أن يتوقف.
- **جلسات على الخادم بدل JWT:** تُخزَّن SHA-256 للتوكن فقط، فيمكن إبطالها فعلياً عند الخروج.
- **حماية في الداتابيز نفسها:** `CHECK`/`UNIQUE`/`FK` وtriggers تمنع تعديل سعر الوحدة المحجوزة، وتجمّد العقد المعتمد وجدول أقساطه، وتجعل الدفعات وتوزيعها وسجل التدقيق append-only، مع فحوصات مؤجلة تضمن تطابق مجموع الأقساط مع السعر النهائي، وتطابق توزيع كل دفعة مع مبلغها. البديل المرفوض: الاكتفاء بفحوصات الكود.
- **منع تكرار الدفعة:** مفتاح `idempotency_key` يُولَّد في الخادم مع كل عرض للنموذج (أو يُرسَل بـ header اسمه `Idempotency-Key`)، وفريد لكل شركة في الداتابيز.

## الافتراضات

- **الدفعة الأولى** هي القسط رقم 0 وتستحق في تاريخ بداية العقد (لا يُولَّد لها صف إذا كانت صفراً).
- **31 يناير:** استحقاق القسط n = تاريخ البداية + n شهراً، مقصوص لآخر يوم في الشهر، ويُحسب دائماً من التاريخ الأصلي. فالبداية في 31 يناير تستحق 28 فبراير ثم 31 مارس ثم 30 أبريل.
- **الخصم الأقصى 5%** يُحسب بأعداد صحيحة (التقريب لأعلى). السعر النهائي لا يزيد عن سعر الوحدة.
- **الاعتماد** يتطلب حجزاً ما زال نشطاً، أي أن أمام المحاسب 72 ساعة من وقت الحجز. بعدها يبقى العقد مسودة.
- **الدفعة الزائدة عن المتبقي** تُرفض برسالة فيها المتبقي، ولا تتحول إلى رصيد دائن. القسط المتأخر يظهر `overdue` ولو كان مدفوعاً جزئياً، وهو أصلاً الأقدم في التوزيع.
- **الصلاحيات:** الذي يضيف العميل ويعدّله هو المندوب وحده. المدير والمحاسب يقرآن عملاء شركتهما. المندوب يرى عقوده وحجوزاته فقط.
- **أي سجل يخص شركة أخرى = 404** وليس 403، حتى لا نكشف وجوده.
- **التوقيت:** التخزين UTC، والعرض والتواريخ بتوقيت الرياض.
- **محاولة دخول فاشلة لبريد غير موجود** لا تخص شركة، فلا تظهر في سجل أي مدير، وتبقى في قاعدة البيانات.
- **الحماية من التخمين** تعتمد على `request.remote_addr`؛ خلف proxy فعّل `TRUST_PROXY=1` وقيّد الوصول المباشر للتطبيق.

## الأمان: أهم 3 مخاطر

1. **تسرّب بيانات بين الشركات (IDOR).** كل استعلام يُقيَّد بـ `company_id` المأخوذ من الجلسة في الخادم، عبر `scoped()` و`get_scoped_or_404()` ودوال الخدمات التي تستقبل `company_id` إجبارياً، ولا تقرأ الشركة من الطلب أبداً. الصلاحيات مفروضة بـ `roles_required` على كل endpoint. الحقول غير المسموحة (الحالة، الشركة، السعر الأصلي) ترفضها مخططات Pydantic بـ `extra="forbid"`. اختبارات التكامل تثبت أن الوصول لبيانات شركة أخرى يرجع 404.
2. **فساد مالي: حجز مزدوج، دفعة مكررة، تجاوز المتبقي، تعديل بأثر رجعي.** الأقفال والـ idempotency key وقيود وtriggers الداتابيز المذكورة أعلاه، وكلها داخل transactions. اختبارات بخيوط حقيقية تثبت أن حجزاً واحداً فقط ينجح، وأن دفعتين متزامنتين لا تتجاوزان المتبقي، وأن إعادة إرسال نفس المفتاح تنتج دفعة واحدة.
3. **اختراق الحسابات والجلسات.** كلمات المرور بـ argon2id. الجلسة كوكي `HttpOnly` و`SameSite=Lax` (و`Secure` في الإنتاج)، والخروج يحذف الجلسة من الخادم. حماية CSRF على كل POST. حد للمحاولات الفاشلة (5 لكل بريد و30 لكل IP كل 15 دقيقة)، ورسالة خطأ موحدة وزمن رد موحد. ترويسات أمان وCSP صارم، وهروب تلقائي للمخرجات، وبدون SQL مبني بدمج النصوص، ورسائل خطأ عامة للمستخدم والتفاصيل في سجل الخادم.

سجل التدقيق يغطي: الدخول الفاشل، تغيير الأسعار، اعتماد العقود، الدفعات (وغيرها). يقرؤه مدير الشركة فقط من `/audit`، ولا يمكن تعديله أو حذفه حتى من قاعدة البيانات.

## الاختبارات

`pytest -q`: وحدة (توليد الأقساط، توزيع الدفعات، الانتقالات، التحقق)، وتكامل على PostgreSQL حقيقي: عزل الشركات، الحجز المتزامن، الاعتماد المتزامن، الدفعات المتزامنة وتكرار المفتاح، حماية الداتابيز، الصلاحيات، الجلسات والـ CSRF. GitHub Actions يشغّل `ruff` و`pytest` و`pip-audit`، ومعها smoke test يقيم التطبيق على قاعدة فارغة (migrations + seed + `/healthz`).

## ما لم يُنجز

- **حزمة Docker** (`docker compose up`) التي طلبتها الورقة: استُبدلت بـ `run.sh` بالاتفاق مع الشركة. كنت سأضيف `Dockerfile` بمستخدم غير root، و`docker-compose.yml` بخدمتين (web وpostgres) مع healthcheck، وتشغيل الـ migrations والـ seed في الـ entrypoint.
- **اختبار E2E بـ Playwright** وفحص الأنواع بـ mypy. كنت سأضيف Playwright للمسار حجز ← عقد ← اعتماد ← دفعة، وmypy مع إضافة SQLAlchemy.
- **تصحيح الأخطاء المالية:** لا حذف ولا تعديل للدفعة (حسب الورقة). كنت سأضيف قيداً عكسياً (reversal) بصلاحية مدير.
- **تعديل المسودة وإلغاؤها**، وتحويل الدفعة الزائدة لرصيد، وإلغاء الحجز يدوياً.
- **بوابة للعميل** لرؤية أقساطه: دور `client` جديد وربطه بسجل العميل، وشاشات قراءة فقط.
- **Rate limiting خارج الداتابيز** (Redis)، وHTTPS، وإدارة أسرار حقيقية.
- **انتهاء الحجز عبر job دوري** إذا كبر الحجم.
